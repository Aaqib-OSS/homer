# ADR-0114: The image's Python runtime installs from a hash-pinned lock, and CI tests and audits that lock

## Context and Problem Statement

The server image (`app/Dockerfile`, slim stage, ADR-0094) installed `clients/python` with a plain
`pip install`, resolving `langgraph` and `langgraph-checkpoint-sqlite` at build time. On the
image's Alpine (musl) base that resolve ended on langgraph 1.1.10, langgraph-checkpoint 2.1.2,
langgraph-checkpoint-sqlite 2.0.7 and langgraph-sdk 0.3.15, the last three with published
advisories. Since 2.0.8, langgraph-checkpoint-sqlite requires `sqlite-vec`, whose current release
(0.1.9) ships manylinux, macOS and Windows wheels but no musllinux wheel and no sdist, so pip on
musl backtracked to the last release without it. CI (`homer-python-tests`, glibc) resolved
langgraph 1.2.22, langgraph-checkpoint 4.3.2, langgraph-checkpoint-sqlite 3.1.3 and langgraph-sdk
0.4.14 instead, so the tests and `pip-audit` covered versions the image did not ship. The first
grype scan found it (ADR-0113). `homer_langgraph` never imports `sqlite-vec`: only
`langgraph.store.sqlite` (the vector-search `SqliteStore`) does, while the runtime uses
`langgraph.checkpoint.sqlite`.

## Decision Drivers

- The image ships the versions CI tests and audits, on amd64 and arm64.
- What reaches the image from PyPI at build time is decided in review, not at build time.
  This is the trust boundary the change crosses: a new or replaced release on the index.
- The fix keeps the Alpine base (ADR-0015) and needs no build toolchain in the image.
- Pins stay current without manual work.

## Considered Options

- **A: a hash-pinned universal lock without `sqlite-vec`.** `clients/python/requirements.lock`,
  generated by `uv pip compile` with `--universal --generate-hashes --no-emit-package=sqlite-vec`;
  the image and CI install it with `--require-hashes --no-deps`.
- **B: a Debian (glibc) base for the server image**, where the newest line resolves.
- **C: build `sqlite-vec` from source** in the image.
- **D: exact pins in `pyproject.toml` or a requirements file, without hashes.**

## Decision Outcome

Chosen: **A**. The slim stage installs the lock with `pip install --require-hashes --no-deps -r
requirements.lock`, then `homer_langgraph` itself with `--no-deps --no-build-isolation`, built by
the setuptools Alpine's `py3-pip` brings. The image never resolves. `homer-python-tests` installs
the same lock the same way, so a dependency missing from the lock fails the tests, and runs
`pip-audit --require-hashes --disable-pip -r requirements.lock`, auditing the tree the image
ships instead of a fresh resolve. Renovate's `pip-compile` manager reads the command from the
lock's header and refreshes it weekly (lock file maintenance); a change to `pyproject.toml`
regenerates it in the same commit.

The lock holds every distribution's hash for each pinned version, so one file installs on musl
and glibc, amd64 and arm64. A version whose native dependencies ship no musllinux wheel fails
the image build rather than silently backtracking.

**Why not the others:**

- **B** moves every image off the base ADR-0015 chose, and still leaves the image resolving at
  build time, untested and unaudited.
- **C** needs a C toolchain in the image or a build stage, for a library the runtime never
  loads.
- **D** keeps the release on the index trusted at build time, and pins without a lock leave the
  transitive tree unpinned.

### Consequences

- Good: the image ships langgraph 1.2.22, langgraph-checkpoint 4.3.2,
  langgraph-checkpoint-sqlite 3.1.3 and langgraph-sdk 0.4.14 at the time of the change, none with
  a known advisory.
- Good: a thread parked under the old line reads and resumes under the new one. The fixture
  `homer_langgraph/tests/fixtures/checkpoints-lg1.1.10.sqlite`, written by the runtime under the
  old versions, keeps this tested (`test_checkpoint_upgrade.py`).
- Good: CI's tests and audit judge exactly the runtime dependencies the image ships.
- Bad: `pip check` reports `sqlite-vec` missing, and `SqliteStore` cannot be used from the image.
  A graph that wants vector search brings its own runtime.
- Bad: the lock's `packaging` replaces the apk copy `py3-pip` installs, so the apk database names
  a version the image no longer has.
- Bad: the test extra (`pytest`) is installed unpinned in CI; it never ships.
- Bad: the installer itself stays outside the lock: `py3-pip`'s pip and setuptools (with the
  wheel and jaraco.context it vendors) come from Alpine and are judged only by the image scan.
